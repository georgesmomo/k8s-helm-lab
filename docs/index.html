      Kubernetes has a reputation for being hard. Most of that comes from learning it backwards: copying a Helm command from a README, watching it work, and having no idea what to do the day it does not. This course goes the other way round. You start from the idea that makes everything else click (you describe a desired state, and controllers make it happen), you meet every object with its reason to exist, and you write them by hand before letting Helm generate them.

      Each station follows the same rhythm: a plain-language explanation with an analogy, the precise technical version, how real companies use it, where it hurts, and a short quiz. The deep reference lives in concept sheets you can open when you need them (104 of them, all searchable from the concept index).

      The declarative model and the reconciliation loop

      30 minutes, the one idea everything else rests on
      By the end of this station you can
      • explain the difference between giving orders and declaring a state;
      • describe what a controller does, and why that makes Kubernetes self-healing;
      • use that idea as your first debugging question.
      Think of a thermostat

      You never tell a heating system "burn gas for 12 minutes". You set 21 °C and walk away. The thermostat measures the room, compares it with what you asked for, and acts on the difference, forever. Open a window and it simply works harder. Kubernetes is a building full of thermostats.

      With Kubernetes you do not give orders ("start three containers"). You describe a state ("I want three replicas of this image") and store it in the cluster. Small programs called controllers constantly compare that spec with the real status and fix the gap. That endless loop is called reconciliation, and it is why Kubernetes heals itself: a crashed pod, a lost node, a deleted object are all just gaps to close.

      It is also the key to every debugging session you will ever have. When something does not work, the question is never "what command failed?" but "which controller cannot converge, and why?"

      Four words to own

      Object
      An entry in the API (Pod, Deployment, Service...) with apiVersion, kind, metadata, spec (what you want) and status (what is).
      Controller
      A program that watches one kind of object and acts until status matches spec. Operators are controllers written for one particular piece of software.
      Labels
      The glue of the system: a Service finds its pods, a Deployment its ReplicaSets, through label selectors.
      Idempotence
      Applying the same file twice changes nothing. That is what makes GitOps, Helm and CI/CD safe to run again and again.
      In real companies

      The desired state does not live in someone's terminal history: it lives in git. A pipeline or a GitOps agent such as Argo CD applies it, and any manual change in the cluster is treated as drift to be corrected. You will see why in the labs.

      Think of an airport

      The control tower (the control plane) never flies a plane. It keeps the official flight board (etcd), answers every radio call at a single desk (the API server), assigns gates (the scheduler) and has supervisors checking that every scheduled flight actually exists (the controllers). At each gate, a ground crew (the kubelet) does the real work and reports back to the tower.

      A cluster has two kinds of machines. The control plane stores state and makes decisions; the worker nodes run your pods. On the lab's kind cluster each "machine" is a Docker container, but everything else is identical to a real kubeadm cluster.

      kube-apiserverThe single front door of the cluster: a REST API that checks, authorizes and stores every object in etcd.
      Why it exists
      Everything goes through it: kubectl, controllers, kubelets, Helm, Argo CD. No component talks to etcd directly, except the API server.
      In real companies
      In production it runs as several copies behind a load balancer (high availability). On EKS, AKS or GKE the provider runs it for you: you only see its URL.
      How it works
      Path of a request: authentication (client certificate, OIDC token, ServiceAccount token) → authorization (RBAC) → mutating admission (mutating webhooks and policies) → schema validation → validating admission (validating webhooks, ValidatingAdmissionPolicy, Pod Security) → write to etcd. Health: kubectl get --raw /livez and /readyz.
      Limits and pitfalls
      If it goes down, running pods keep running but nothing can change any more: no deployments, no rescheduling. A broken admission webhook with failurePolicy: Fail can block the whole cluster.
      Exam tip
      CKA: be able to read its static manifest /etc/kubernetes/manifests/kube-apiserver.yaml and its flags (--etcd-servers, --service-cluster-ip-range, --authorization-mode).
      etcdA distributed key-value database (Raft consensus) that stores the whole state of the cluster: objects, Secrets, configuration.
      Why it exists
      It is the cluster's memory. Losing etcd without a backup means losing the definition of every application.
      In real companies
      3 or 5 members (an odd number) to survive 1 or 2 failures. Scheduled snapshot backups, encryption of Secrets at rest, fast SSD disks (write latency is critical).
      How it works
      etcdctl snapshot save / etcdutl snapshot restore, with the certificates from /etc/kubernetes/pki/etcd/. On kubeadm, etcd is a static pod of the control plane.
      Limits and pitfalls
      Never edit it by hand. High disk latency slows the whole cluster down. Secrets are stored in plain text in etcd (base64 is only how the API shows them) unless an EncryptionConfiguration is enabled.
      Exam tip
      Backing up and restoring etcd is a CKA classic: the right certificates, a new --data-dir for the restore, then point the etcd manifest at it.
      kube-schedulerThe component that picks the node on which each new pod will run.
      Why it exists
      Place pods where there is room (based on requests), while respecting constraints and preferences (affinities, taints, spreading).
      In real companies
      Understanding why a pod stays Pending, spreading replicas across zones, isolating GPU or sensitive workloads on dedicated nodes.
      How it works
      Two phases: filtering (which nodes are possible) then scoring (which one is best). It writes spec.nodeName; the kubelet of that node does the rest. Reasons for failure appear in the FailedScheduling event.
      Limits and pitfalls
      It never moves a pod that is already placed (the descheduler, a separate project, can). It reasons on requests, not on real usage.
      Exam tip
      A pod with spec.nodeName set by hand bypasses the scheduler. So do static pods.
      kube-controller-managerOne process that bundles the built-in controllers: Deployment, ReplicaSet, Node, Job, EndpointSlice, ServiceAccount, garbage collector...
      Why it exists
      Make the real state converge towards the desired state, in a loop: a pod is missing? create one. A node stopped answering? mark its pods for replacement.
      In real companies
      It does the work when you change an image or a replica count. Operators (CRD + controller) use exactly the same model for other software.
      How it works
      Loop: observe → compare → act, always through the API. Several instances in HA with leader election (a Lease object in kube-system).
      Limits and pitfalls
      It only acts through the API: if it stops, nothing heals on its own (no new pod is ever created).
      cloud-controller-managerThe controllers that are specific to a cloud provider, kept outside the Kubernetes core.
      Why it exists
      Create a real load balancer for a LoadBalancer Service, fill in node zones and addresses, remove nodes that were destroyed in the cloud.
      In real companies
      Present on EKS, AKS, GKE and OpenStack; absent on kind (which is why a LoadBalancer Service stays <pending> there without cloud-provider-kind or MetalLB).
      How it works
      Deployed and run by the provider on managed services. On premises, MetalLB or kube-vip play the load balancer role.
      Limits and pitfalls
      The annotations of LoadBalancer Services are different for every cloud.
      kubeletThe agent installed on every node: it receives the pods assigned to its node and makes them exist through the container runtime.
      Why it exists
      Start and watch containers, run probes, mount volumes, report node and pod status to the API.
      In real companies
      First suspect when a node is NotReady: systemctl status kubelet, journalctl -u kubelet. It is also the kubelet that evicts pods when the node runs short of memory or disk.
      How it works
      A systemd service (not a pod). Configuration in /var/lib/kubelet/config.yaml. It also runs the static pods found in /etc/kubernetes/manifests: that is how a kubeadm control plane boots.
      Limits and pitfalls
      If the kubelet stops, containers keep running, but the node turns NotReady and, after a while, its pods are recreated elsewhere.
      Exam tip
      Troubleshooting a NotReady node: kubelet stopped, expired certificate, missing runtime, swap, bad configuration.
      kube-proxyA DaemonSet that programs each node's network (iptables, nftables or IPVS) so that a Service's virtual IP leads to its pods.
      Why it exists
      Make Services reachable and spread the load across their ready pods.
      In real companies
      Modern CNIs (Cilium in eBPF mode) can replace it entirely for better performance.
      How it works
      It watches Services and EndpointSlices and rewrites the rules. The mode is visible in the kube-proxy ConfigMap in kube-system. The nftables mode is GA since Kubernetes 1.33 (iptables is still the default).
      Limits and pitfalls
      It is not an application proxy: no retries, no HTTP awareness. For layer-7 routing you need a Gateway, an Ingress or a service mesh.
      Container runtime (CRI, containerd)The software that pulls images and actually starts containers, driven by the kubelet through the CRI interface.
      Why it exists
      Keep Kubernetes independent of the implementation: containerd and CRI-O are the two standard runtimes.
      In real companies
      Since dockershim was removed (1.24), Docker is no longer the node runtime; images built with Docker still work (OCI format).
      How it works
      crictl ps, crictl images, crictl logs on the node to look underneath Kubernetes. The low-level runtime (runc) creates the namespaces and cgroups.
      Limits and pitfalls
      docker ps on a modern Kubernetes node shows nothing about pods: use crictl.
      CNI (pod networking)The network plugin that gives every pod an IP and connects pods across nodes: Cilium, Calico, Flannel, kindnet, cloud CNIs (VPC CNI, Azure CNI).
      Why it exists
      Guarantee the Kubernetes network model: every pod has its own IP and can reach every other pod without NAT.
      In real companies
      The CNI decides whether NetworkPolicies are enforced, network observability (Hubble), encryption, performance. An architecture choice that is hard to change later.
      How it works
      Installed right after kubeadm init (until then, nodes stay NotReady). Config in /etc/cni/net.d, binaries in /opt/cni/bin.
      Limits and pitfalls
      A NetworkPolicy only has an effect if the CNI supports it (Flannel alone does not). Pod IP ranges must not overlap with the company network.
      CoreDNSThe cluster DNS server, deployed in kube-system.
      Why it exists
      Resolve service.namespace.svc.cluster.local to the Service IP, and external names through the upstream DNS.
      In real companies
      DNS latency or errors show up as application timeouts everywhere. NodeLocal DNSCache is often added on large clusters.
      How it works
      Configured by the coredns ConfigMap (Corefile). Test: kubectl run dns --rm -it --image=busybox:1.36 --restart=Never -- nslookup kubernetes.default.
      Limits and pitfalls
      ndots:5 in the pods' /etc/resolv.conf multiplies queries for external names; use fully qualified names ending with a dot for heavy external calls.
      CSI (storage drivers)The standard interface for storage drivers: EBS, Azure Disk, Persistent Disk, Ceph, NetApp, local-path...
      Why it exists
      Create, attach and mount volumes on demand when an application asks for them.
      In real companies
      Databases on StatefulSets with cloud disks, volume snapshots for backups, encrypted disks.
      How it works
      The driver is deployed (a controller plus a DaemonSet) and referenced by a StorageClass (provisioner: ebs.csi.aws.com).
      Limits and pitfalls
      A cloud disk lives in one zone: a pod that moves to another zone cannot follow it (hence volumeBindingMode: WaitForFirstConsumer).

      The life of a pod

      Probes are how you tell Kubernetes what "started", "ready" and "alive" mean for your app. The lab Deployment uses all three:

                startupProbe:
            httpGet: {path: /healthz, port: http}
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:                 # removes the pod from the Service when it fails
            httpGet: {path: /readyz, port: http}
            periodSeconds: 5
          livenessProbe:                  # restarts the container when it fails
            httpGet: {path: /healthz, port: http}
            periodSeconds: 10
            failureThreshold: 3
      Think of a restaurant

      The startup probe asks "is the kitchen open yet?". The readiness probe asks "can you take a new table right now?" (if not, the host stops seating people there, but nobody is fired). The liveness probe asks "is anyone actually in the kitchen?" (if not, the shift is replaced). Asking the liveness question about the supplier's delivery truck would be absurd, and that is exactly what a liveness probe on your database does.

      PodThe smallest deployable unit: one or more containers that share the same IP, network and volumes, always scheduled together on one node.
      Why it exists
      Run an application process with its environment (variables, volumes, probes, resources, identity).
      In real companies
      You almost never create a bare pod: a controller (Deployment, StatefulSet, Job) creates and recreates it. A pod is ephemeral and disposable.
      How it works
      Lifecycle: Pending → Running → Succeeded/Failed. kubectl get pod -o wide, describe, logs, exec. Containers have their own states (Waiting, Running, Terminated) with a reason.
      Limits and pitfalls
      A deleted pod without a controller is not recreated. Its IP changes every time it is recreated: never hard-code it, use a Service.
      Probes (startup, readiness, liveness)Checks run by the kubelet. Startup: has the app started? Readiness: can it receive traffic? Liveness: is it stuck?
      Why it exists
      Never send traffic to a pod that is not ready, restart a frozen container, give slow apps time to start.
      In real companies
      Readiness on an endpoint that checks the dependencies the app really needs; liveness on a very simple endpoint (the process answers). Startup for slow starters such as JVMs.
      How it works
      httpGet, tcpSocket, exec or grpc; periodSeconds, timeoutSeconds, failureThreshold. Readiness fails → the pod leaves the Service endpoints. Liveness fails → the container is killed and restarted. While a startupProbe has not succeeded, the other two are not run.
      Limits and pitfalls
      A liveness probe that tests the database: one database outage restarts your whole fleet. Liveness without a startupProbe on a slow app: restart loop (scenario 10).
      Exam tip
      Be able to write all three probes and predict the effect of each.
      Init containersContainers that run one after the other, each until it succeeds, before the main containers of the pod start.
      Why it exists
      Prepare things: wait for a dependency, download configuration, fix permissions on a volume.
      In real companies
      Wait for the database to answer before starting; fetch certificates from Vault.
      How it works
      spec.initContainers. Status Init:0/1 in kubectl get pods; logs with -c <name>.
      Limits and pitfalls
      A failing init container blocks the pod in Init:CrashLoopBackOff. Prefer apps that know how to retry their own connections.
      Native sidecarsHelper containers that run for the whole life of the pod: proxy, log agent, file sync.
      Why it exists
      Add a cross-cutting feature without changing the application.
      In real companies
      Service-mesh proxies, collection agents, token renewal.
      How it works
      Since 1.29 (GA in 1.33): an initContainer with restartPolicy: Always becomes a sidecar, started before and stopped after the main containers.
      Limits and pitfalls
      They use resources in every pod. "Sidecar-less" meshes (Istio ambient, Cilium) are gaining ground.

      Deployments and rolling updates

      A Deployment never touches pods itself. Each version of its pod template gets its own ReplicaSet; a rolling update scales the new ReplicaSet up and the old one down, within two limits you choose: maxSurge (how many extra pods you may add) and maxUnavailable (how many may be missing). The old ReplicaSet is kept at 0 replicas, which is what makes kubectl rollout undo instant.

      ReplicaSetThe controller that keeps a given number of identical pods running.
      Why it exists
      Make sure there are always N copies: a pod dies, it creates another.
      In real companies
      You do not handle it directly: every version of a Deployment creates a ReplicaSet, and the history of ReplicaSets is what makes rollback possible.
      How it works
      kubectl get rs: DESIRED / CURRENT / READY. Name = <deployment>-<hash of the pod template>.
      Limits and pitfalls
      Editing a ReplicaSet owned by a Deployment is pointless: the Deployment will put it back.
      DeploymentThe standard controller for stateless applications: it manages ReplicaSets to roll out, update and roll back.
      Why it exists
      Updates without downtime, rollback, scaling.
      In real companies
      Web APIs, workers, front ends: the large majority of company workloads.
      How it works
      Changing the pod template (image, env, config reference) triggers a rolling update. kubectl rollout status / history / undo / restart. strategy: RollingUpdate (maxSurge, maxUnavailable) or Recreate.
      Limits and pitfalls
      Changing a mounted ConfigMap does not restart the pods: that is why the Helm chart has a checksum annotation. replicas in the YAML fights with an HPA: let the HPA own it.
      Exam tip
      rollout undo --to-revision, set image, scale: quick manipulations expected in the exam.
      Rolling update and rollbackReplacing old pods with new ones progressively, and going back to a previous version.
      Why it exists
      Ship continuously without interrupting the service.
      In real companies
      maxUnavailable: 0 + maxSurge: 1 + a reliable readiness probe = capacity never drops. For advanced canary or blue/green: Argo Rollouts, Flagger, or two Deployments behind the Gateway API.
      How it works
      kubectl rollout status deploy/x (waits for the end) · rollout history · rollout undo [--to-revision=2] · rollout pause/resume.
      Limits and pitfalls
      Rollback restores the previous pod template, not your data nor ConfigMaps changed on the side. A stuck rollout (readiness failing) waits for progressDeadlineSeconds and is then marked as failed, without rolling back on its own.
      StatefulSetThe controller for stateful applications: stable names (app-0, app-1), one volume per pod, ordered startup and shutdown.
      Why it exists
      Databases, message queues, clustered software (Kafka, Elasticsearch, PostgreSQL with an operator).
      In real companies
      Companies avoid running a database on Kubernetes by hand, without an operator (CloudNativePG, Strimzi); many prefer a managed database.
      How it works
      serviceName (a headless Service), volumeClaimTemplates. Per-pod DNS: app-0.app.ns.svc.cluster.local. RollingUpdate goes in reverse order.
      Limits and pitfalls
      Deleting a StatefulSet does not delete its PVCs (data protection). Scaling does not replicate data: the application must do that itself.
      DaemonSetOne pod per node (or per selected node), added automatically to every new node.
      Why it exists
      Infrastructure agents: log collection, node monitoring, CNI, kube-proxy, CSI drivers, runtime security (Falco).
      In real companies
      Fluent Bit and node-exporter run as DaemonSets on every production cluster.
      How it works
      kubectl get ds -A. Add tolerations if it must also run on control-plane nodes.
      Limits and pitfalls
      Every DaemonSet uses resources on every node: count them when sizing nodes.
      JobRun one or more pods until they succeed.
      Why it exists
      One-off tasks: schema migration, import, smoke test, batch processing.
      In real companies
      Database migration before a release (a Helm hook), post-deployment smoke test, parallel batch computation (completions, parallelism).
      How it works
      backoffLimit (retries), activeDeadlineSeconds (max duration), ttlSecondsAfterFinished (clean-up), restartPolicy: Never or OnFailure. kubectl wait --for=condition=complete job/x.
      Limits and pitfalls
      Without ttlSecondsAfterFinished, finished Jobs pile up. A task must be idempotent: it may run again.
      CronJobA Job scheduled with a cron expression.
      Why it exists
      Backups, purges, reports, nightly checks.
      In real companies
      Database backup at 3 a.m., weekly clean-up of temporary files.
      How it works
      schedule, timeZone, concurrencyPolicy (Allow, Forbid, Replace), startingDeadlineSeconds, history limits. kubectl create job --from=cronjob/x test runs it now.
      Limits and pitfalls
      Without timeZone, the time is the controller's (often UTC). Forbid prevents two long runs from overlapping.

      ConfigMapAn object that stores non-sensitive configuration (key/value pairs or whole files).
      Why it exists
      Keep configuration out of the image: same image in dev and prod, different configuration.
      In real companies
      Log level, URLs of other services, application config files, simple feature flags.
      How it works
      Injected as variables (env / envFrom) or as files (volume). kubectl create configmap x --from-file=... --from-literal=...
      Limits and pitfalls
      Environment variables are frozen when the container starts; mounted files are updated (after a delay) except with subPath. Max size 1 MiB. immutable: true for performance and safety.
      SecretAn object for sensitive data: passwords, tokens, TLS certificates, registry credentials.
      Why it exists
      Give secrets to pods without putting them in the image or in the application YAML.
      In real companies
      Never in plain text in git: External Secrets Operator (Vault, AWS/GCP/Azure secret managers), Sealed Secrets or SOPS. Encryption at rest enabled for etcd.
      How it works
      Types: Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson. data is base64, stringData is plain text on write. Mount as a volume (preferred) or as env.
      Limits and pitfalls
      base64 is not encryption. Anyone who can create a pod in the namespace can read the Secrets it can mount: the RBAC right "get secrets" is sensitive.

      Why it exists
      Richer logs, instance identification, adapting to the memory you were given.
      In real companies
      The lab injects POD_NAME and NODE_NAME: the API's answer tells you which pod replied.
      How it works
      env.valueFrom.fieldRef (metadata.name, spec.nodeName, status.podIP) or resourceFieldRef (limits.memory).
      Limits and pitfalls
      Read-only, and limited to a handful of fields.

      Decouple clients from pods: pods come and go, the Service address stays.
      In real companies
      Every internal component (API, database, cache) is reached through its Service: http://kubelab.kubelab.svc.cluster.local.
      How it works
      selector + ports (Service port → pod targetPort, preferably by name). kubectl get svc, kubectl get endpointslices -l kubernetes.io/service-name=x.

      Only ready pods (readiness passing) receive traffic. A Service IP usually does not answer ping in iptables/nftables mode (it is not a real interface): do not use ping as a test.
      NodePort ServiceA Service opened on one port (30000-32767) of every node.

      Simple exposure outside the cluster, without a load balancer.
      In real companies
      Labs, kind, or behind an external load balancer configured by hand. Rare as direct production exposure.

      type: NodePort, nodePort optional. Access: <any node IP>:<nodePort>.
      Limits and pitfalls
      High port numbers, a node IP you must know, no TLS and no HTTP routing.
      LoadBalancer ServiceA Service for which the cloud creates a real load balancer with a public or internal IP.
      Why it exists
      Expose a TCP/UDP service outside the cluster.
      In real companies
      Expose the Gateway or ingress controller (one LB for all HTTP apps), or a non-HTTP service (MQTT, a database).
      How it works
      type: LoadBalancer plus cloud annotations (internal, subnet...). EXTERNAL-IP appears in kubectl get svc.
      Limits and pitfalls
      One LB per Service is expensive: for HTTP, share one through the Gateway API. On premises: MetalLB or kube-vip.
      Headless ServiceA Service with clusterIP: None: no virtual IP, DNS returns the pod IPs directly.
      Why it exists
      Let the client choose the pod (clustered databases) and give each StatefulSet pod its own DNS name.
      In real companies
      kubelab-db-0.kubelab-db.kubelab.svc.cluster.local in the StatefulSet lab.
      How it works
      clusterIP: None + selector; referenced by the StatefulSet's serviceName.
      Limits and pitfalls
      No load balancing by kube-proxy.
      EndpointSlicesThe objects listing the addresses of the pods behind a Service, with their state (ready, serving, terminating).
      Why it exists
      The concrete link between a Service and its pods, read by kube-proxy and ingress/gateway controllers.
      In real companies
      First reflex when a Service "does not answer": does it have endpoints?
      How it works
      kubectl get endpointslices -l kubernetes.io/service-name=kubelab -o wide. (The old Endpoints object is deprecated since 1.33.)
      Limits and pitfalls
      Empty means: wrong selector, pods not ready, or wrong namespace.
      Service DNSAutomatic naming: <service>.<namespace>.svc.cluster.local, plus <pod>.<service>... for headless Services.
      Why it exists
      Reach a service by name from any pod.
      In real companies
      In the same namespace, kubelab is enough; from another one, kubelab.kubelab.
      How it works
      Test with nslookup kubelab.kubelab from a debug pod. The cluster domain (cluster.local) is chosen at install time.
      Limits and pitfalls
      DNS problems look like network problems: always test name resolution before the connection.

      IngressThe historical resource for exposing HTTP(S) services with host and path routing, implemented by an ingress controller.
      Why it exists
      One HTTP entry point, central TLS, routing to many services.
      In real companies
      Still everywhere. Note: the ingress-nginx project (the most widely used controller) was retired in March 2026; new platforms move to the Gateway API.
      How it works
      rules (host, paths) + tls (a Secret) + ingressClassName. The controller (Traefik, HAProxy, F5 NGINX, cloud controllers) reads the objects and configures its proxy.
      Limits and pitfalls
      Advanced features come through controller-specific annotations: not portable.
      Exam tip
      Still in the CKA/CKAD curriculum next to the Gateway API.
      Gateway APIThe successor of Ingress: separate resources per role (GatewayClass for infrastructure, Gateway for the platform team, HTTPRoute for application teams).
      Why it exists
      Rich, portable HTTP, gRPC and TCP routing (headers, weights for canaries, redirects) without proprietary annotations.
      In real companies
      The standard for new platforms: Envoy Gateway, Cilium, Istio, Traefik, NGINX Gateway Fabric, cloud controllers. The platform team owns the Gateway, every team owns its HTTPRoutes.
      How it works
      Install the CRDs and a controller, create a Gateway (listeners, TLS), then HTTPRoutes (parentRefs, hostnames, rules, backendRefs with weight). See manifests/10-httproute.yaml and the chart.
      Limits and pitfalls
      The CRDs are not installed by default. Routes across namespaces need explicit consent (allowedRoutes, ReferenceGrant).
      Exam tip
      In the CKA curriculum since 2025.

      A firewall between pods

      Without a NetworkPolicy, any compromised pod can talk to every other pod in the cluster. The lab namespace starts from zero trust: deny all incoming traffic, then allow only pods labelled role: client to reach port 8080.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: kubelab
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-http-to-kubelab
  namespace: kubelab
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: kubelab
  policyTypes: [Ingress]

        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kubelab
          podSelector:
            matchLabels:
              role: client

        - port: 8080

      PersistentVolume and PersistentVolumeClaimA PV is a piece of storage in the cluster. A PVC is a pod's request ("1 GiB, read-write"). Kubernetes binds one to the other.
      Why it exists
      Separate what the application asks for from how storage is provided.
      In real companies
      Dynamic provisioning: the PVC creates the disk automatically through the StorageClass. Manual PVs remain for existing NFS shares.
      How it works
      kubectl get pvc,pv. PVC states: Pending, Bound, Lost. PV states: Available, Bound, Released, Failed. accessModes, resources.requests.storage, storageClassName.
      Limits and pitfalls
      A Pending PVC keeps its pod Pending (scenario 08). Growing a volume needs allowVolumeExpansion on the StorageClass; shrinking is impossible.
      StorageClassA storage "profile": which CSI driver, which disk type, which policy.
      Why it exists
      Offer several tiers (standard, SSD, encrypted, replicated) and provision on demand.
      In real companies
      One default StorageClass (annotation is-default-class), a fast one for databases, one with reclaimPolicy: Retain for critical data.
      How it works
      provisioner, parameters, reclaimPolicy (Delete or Retain), volumeBindingMode (WaitForFirstConsumer recommended), allowVolumeExpansion.
      Limits and pitfalls
      reclaimPolicy: Delete deletes the disk with the PVC: beware of namespace deletions.
      Access modes and reclaim policyAccess modes: ReadWriteOnce (one node), ReadOnlyMany, ReadWriteMany (many nodes), ReadWriteOncePod (a single pod). Reclaim policy: what happens to the volume when its PVC is deleted.
      Why it exists
      Pick the right storage for the sharing you need.
      In real companies
      Cloud disks are RWO; sharing between pods needs RWX (NFS, EFS, Azure Files, CephFS).
      How it works
      accessModes in the PVC; reclaimPolicy in the StorageClass or the PV.
      Limits and pitfalls
      RWO does not mean a single pod: several pods on the same node can mount it. Use RWOP to guarantee exclusivity.
      Exam tip
      Part of the CKA Storage domain (10%).
      emptyDir and ephemeral volumesAn empty directory created with the pod and destroyed with it.
      Why it exists
      Cache, temporary files, sharing files between containers of one pod; essential with readOnlyRootFilesystem.
      In real companies
      /tmp as an emptyDir for an app whose image is read-only.
      How it works
      volumes: - name: tmp, emptyDir: {sizeLimit: 100Mi} (or medium: Memory).
      Limits and pitfalls
      Counted in the node's ephemeral storage: without sizeLimit, one pod can fill the disk and cause evictions.
      VolumeSnapshotsVolume snapshots through the API (VolumeSnapshot, VolumeSnapshotClass), when the CSI driver supports them.
      Why it exists
      Consistent backups and data cloning (create a PVC from a snapshot).
      In real companies
      A snapshot before a database migration; Velero uses them for volume backups.
      How it works
      Install the CRDs and the snapshot-controller, then create a VolumeSnapshot that points to a PVC.
      Limits and pitfalls
      A disk snapshot is not necessarily application-consistent (a database in the middle of a write).

      Resources, placement and elasticity

      2 hours, where pods run and with how much
      By the end of this station you can
      • set requests and limits on purpose and predict a pod's QoS class;
      • steer placement with affinity, taints and spreading;
      • scale with the HPA and keep availability with PDBs, quotas and LimitRanges.

      The scheduler only reasons about requests, never about real usage. Get them wrong and everything downstream goes wrong: pods that never get placed, nodes that are full of idle reservations, an autoscaler that cannot compute anything.

      QoS class calculator

      Fill in the resources of a single-container pod (leave a field empty to omit it). Kubernetes computes the QoS class, which decides who is evicted first when a node runs out of memory.

      In real companies

      Requests on everything, a memory limit on everything, and usually no CPU limit: spare CPU is shared fairly by requests, while a CPU limit throttles your app even when the node is idle. The values come from measurement (kubectl top, Prometheus, the VPA in recommendation mode), not from guesses.

      Requests and limitsRequests: what the scheduler reserves for the container. Limits: the ceiling it cannot go above.
      Why it exists
      Place pods correctly, stop one pod from starving its neighbours, plan capacity and costs.
      In real companies
      Always set CPU and memory requests; set a memory limit (going over = OOMKilled); often no CPU limit (spare CPU is simply shared, a limit causes throttling).
      How it works
      resources.requests / limits, units m (millicores) and Mi/Gi. Compare with real usage with kubectl top pods; the VPA in recommendation mode helps calibrate.
      Limits and pitfalls
      Requests too high: Pending pods and wasted money. Too low: overloaded nodes and evictions. A memory limit too tight: OOMKilled (scenario 03).
      Exam tip
      Know the chain requests → QoS class → eviction order.
      QoS classesGuaranteed (requests = limits for CPU and memory in every container), Burstable (at least one request or limit), BestEffort (nothing at all). Computed automatically.
      Why it exists
      Decide who gets evicted first when a node runs out of memory.
      In real companies
      Databases and critical components in Guaranteed; web apps in Burstable; never BestEffort in production (a LimitRange prevents it).
      How it works
      kubectl get pod x -o jsonpath='{.status.qosClass}'.
      Limits and pitfalls
      Eviction under memory pressure: BestEffort first, then Burstable pods using more than their requests.
      nodeSelector and nodeAffinityForce (required) or nudge (preferred) a pod's placement according to node labels.
      Why it exists
      Send workloads to the right hardware or zone: GPU, ARM, spot nodes, availability zone.
      In real companies
      ML jobs on gpu=true nodes; sensitive apps on a dedicated node pool.
      How it works
      nodeSelector: {disktype: ssd} (simple) or affinity.nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution with operators In, NotIn, Exists.
      Limits and pitfalls
      "IgnoredDuringExecution": changing a node's labels does not move pods already running. An impossible constraint = Pending.
      Pod affinity and anti-affinityPlace a pod close to (or away from) other pods, according to their labels and a topology (node, zone).
      Why it exists
      Put a cache next to its app, or keep replicas apart for high availability.
      In real companies
      A "preferred" anti-affinity between replicas of one app; topologySpreadConstraints often replaces it with finer control.
      How it works
      affinity.podAntiAffinity.preferredDuringSchedulingIgnoredDuringExecution, labelSelector, topologyKey: kubernetes.io/hostname or topology.kubernetes.io/zone.
      Limits and pitfalls
      A "required" anti-affinity with more replicas than nodes leaves pods Pending. Expensive to compute on big clusters.
      Taints and tolerationsA taint pushes pods away from a node; only pods that tolerate it may go there.
      Why it exists
      Reserve nodes (GPU, control plane, dedicated pool) and handle unhealthy nodes.
      In real companies
      GPU nodes tainted gpu=true:NoSchedule; the control plane carries node-role.kubernetes.io/control-plane:NoSchedule; Kubernetes adds node.kubernetes.io/not-ready:NoExecute to failing nodes.
      How it works
      kubectl taint nodes n1 dedicated=batch:NoSchedule (add - at the end to remove it). Effects: NoSchedule, PreferNoSchedule, NoExecute (also evicts pods already there).
      Limits and pitfalls
      A toleration allows, it does not attract: combine it with nodeAffinity to force placement.
      Exam tip
      CKA classic: run a pod on the control plane, or dedicate a node.
      topologySpreadConstraintsA rule that spreads pods evenly across nodes, zones or regions.
      Why it exists
      Survive the loss of a node or a zone without losing every replica.
      In real companies
      Every production app: maxSkew: 1 on topology.kubernetes.io/zone and on kubernetes.io/hostname. The kubelab chart enables it by default.
      How it works
      maxSkew, topologyKey, whenUnsatisfiable (DoNotSchedule or ScheduleAnyway), labelSelector.
      Limits and pitfalls
      DoNotSchedule can leave pods Pending when one zone is short of capacity.
      PriorityClass and preemptionA numeric priority given to pods; a high-priority pod can evict lower-priority pods to find room.
      Why it exists
      Make sure critical components start even on a full cluster.
      In real companies
      Security and monitoring agents get a high priority; batch jobs a low one.
      How it works
      A PriorityClass (value, preemptionPolicy), then priorityClassName in the pod. system-cluster-critical and system-node-critical already exist.
      Limits and pitfalls
      Misused, preemption causes cascades of evictions.

      HorizontalPodAutoscalerA controller that adjusts the replica count from metrics (CPU, memory, business metrics).
      Why it exists
      Absorb traffic peaks without paying for peak capacity all the time.
      In real companies
      Web API: CPU at 70% of requests, min 3, max 20. Business metrics (queue length, requests per second) via KEDA or a Prometheus adapter.
      How it works
      autoscaling/v2: scaleTargetRef, minReplicas, maxReplicas, metrics, behavior (stabilization). Needs metrics-server for CPU and memory. kubectl get hpa shows TARGETS.
      Limits and pitfalls
      Without CPU requests the HPA cannot compute a percentage (<unknown>). Do not also set replicas in the Deployment (conflict on every apply).
      VerticalPodAutoscalerAn add-on that recommends or adjusts requests and limits from observed usage.
      Why it exists
      Calibrate resources without guessing.
      In real companies
      The Off mode (recommendations only) is widely used to choose the right values for charts.
      How it works
      Install the VPA, create a VerticalPodAutoscaler object targeting a Deployment, read status.recommendation. In-place pod resize is GA since 1.35.
      Limits and pitfalls
      Do not combine VPA and HPA on the same CPU metric.
      Cluster Autoscaler and KarpenterComponents that add nodes when pods stay Pending for lack of room, and remove nodes that are under-used.
      Why it exists
      Pay for the capacity you need, when you need it.
      In real companies
      Cluster Autoscaler on node groups (AKS, GKE, EKS); Karpenter (AWS, Azure) directly picks the best machine type.
      How it works
      Configured by the provider or installed with Helm, with min/max bounds per pool.
      Limits and pitfalls
      A pod without requests does not trigger scale-up. PDBs that are too strict prevent nodes from being removed.
      PodDisruptionBudgetThe minimum number of pods to keep available (or the maximum to take down) during a voluntary disruption.
      Why it exists
      Protect availability during drains, cluster upgrades and node scale-down.
      In real companies
      Every app with several replicas: minAvailable: 2 out of 3, or maxUnavailable: 1.
      How it works
      policy/v1 PodDisruptionBudget with a selector. kubectl get pdb: ALLOWED DISRUPTIONS. kubectl drain respects PDBs (eviction API).
      Limits and pitfalls
      A PDB with minAvailable equal to the replica count blocks every drain forever. It does not protect against a node crash (an involuntary disruption).
      ResourceQuotaCeilings per namespace: CPU, memory, number of pods, Services, PVCs, LoadBalancers...
      Why it exists
      Share a cluster between teams without one of them eating everything.
      In real companies
      Every team namespace has a negotiated quota; the platform team follows it on its dashboards.
      How it works
      spec.hard; kubectl describe quota shows Used / Hard. With a quota on requests.cpu, every pod must declare requests (hence the LimitRange).
      Limits and pitfalls
      A pod refused by the quota never appears: the ReplicaSet carries the FailedCreate event (kubectl describe rs).
      LimitRangeDefault values and min/max bounds for resources per container in a namespace.
      Why it exists
      Give requests and limits to pods that have none, and forbid extreme values.
      In real companies
      Paired with the ResourceQuota in every team namespace.
      How it works
      type: Container with default, defaultRequest, min, max.
      Limits and pitfalls
      Applied at creation only: it does not change existing pods.

      The kubelab namespace enforces the restricted profile through three labels. Try to sneak in a plain busybox pod and the API server refuses it, listing everything that is missing:

  name: kubelab

      Encryption at rest, in one file

      Remember that etcd stores Secrets in plain text by default. On a kubeadm cluster, this file passed to the API server with --encryption-provider-config changes that (a cloud KMS provider is the better choice in production):

      apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: [secrets]
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <base64 of a random 32-byte key>
      - identity: {}        # still able to read old, unencrypted Secrets

      Then rewrite the existing Secrets so they get encrypted: kubectl get secrets -A -o json | kubectl replace -f -.

      RBACRole-based access control: Roles (or ClusterRoles) list verbs on resources, RoleBindings give them to users, groups or ServiceAccounts.
      Why it exists
      Apply least privilege to every human and every program.
      In real companies
      Directory groups (OIDC) bound to Roles per namespace: developers read and restart, ops edit, cluster-admin kept rare and audited. One ServiceAccount per application.
      How it works
      Role/RoleBinding (namespace) · ClusterRole/ClusterRoleBinding (cluster). kubectl auth can-i list pods --as=... -n ...; kubectl auth can-i --list. The ClusterRoles view, edit, admin already exist.
      Limits and pitfalls
      There is no "deny" rule: everything adds up. get/list on secrets, create on pods/exec, escalate/bind and impersonate are often as good as admin rights.
      Exam tip
      Create a Role + RoleBinding for a ServiceAccount and check it with auth can-i: almost certain to show up in the exam.
      ServiceAccountThe identity of a pod towards the Kubernetes API (and, through identity federation, towards the cloud).
      Why it exists
      Give an application exactly the rights it needs, and none to those that need none.
      In real companies
      One ServiceAccount per app, automountServiceAccountToken: false if it never calls the API. Workload Identity (GKE), IRSA / Pod Identity (EKS), Workload Identity (AKS) to reach the cloud without keys.
      How it works
      serviceAccountName in the pod. Projected tokens are short-lived and audience-bound. kubectl create token <sa> for a temporary token.
      Limits and pitfalls
      The default ServiceAccount exists in every namespace: never give it rights.
      Pod Security AdmissionThe built-in admission check that applies the Pod Security Standards (privileged, baseline, restricted) per namespace, through labels.
      Why it exists
      Block dangerous pods: privileged, root, hostPath, hostNetwork, extra Linux capabilities.
      In real companies
      restricted in enforce mode for application namespaces, at least baseline elsewhere; privileged only for system namespaces (CNI, node monitoring).
      How it works
      Labels pod-security.kubernetes.io/enforce|audit|warn: restricted on the namespace (see manifests/00-namespace.yaml). Warnings are printed by kubectl apply.
      Limits and pitfalls
      No per-pod exceptions: for finer rules use Kyverno, Gatekeeper or ValidatingAdmissionPolicy.
      securityContextThe Linux security settings of a pod or container: user, group, capabilities, file system, seccomp.
      Why it exists
      Reduce what an attacker can do after compromising the container.
      In real companies
      runAsNonRoot, allowPrivilegeEscalation: false, capabilities.drop: [ALL], seccompProfile: RuntimeDefault: the baseline required by the restricted profile. readOnlyRootFilesystem: true on top is recommended by most audits, but restricted does not require it.
      How it works
      spec.securityContext (pod: runAsUser, fsGroup, seccomp) and containers[].securityContext. The lab and the chart apply all of it.
      Limits and pitfalls
      readOnlyRootFilesystem breaks apps that write to /tmp: mount an emptyDir there.
      Admission control and policiesThe steps that modify (mutating) or validate (validating) every object before it is stored: built-in plugins, webhooks, ValidatingAdmissionPolicy (CEL), Kyverno, OPA Gatekeeper.
      Why it exists
      Enforce company rules automatically: allowed registries, mandatory labels, required limits, signed images.
      In real companies
      Kyverno or Gatekeeper on every cluster, policies versioned in git, audit mode first and enforce later.
      How it works
      Order: mutating admission → schema validation → validating admission. ValidatingAdmissionPolicy (GA since 1.30) gives CEL rules with no webhook; Kyverno uses ClusterPolicy objects in YAML. Test with kubectl apply --dry-run=server.
      Limits and pitfalls
      An unavailable webhook with failurePolicy: Fail blocks creations: exclude kube-system and run it highly available.
      Encrypting Secrets at restThe API server setting that encrypts chosen resources (Secrets) before writing them to etcd.
      Why it exists
      So that a stolen etcd backup or disk does not reveal your secrets.
      In real companies
      On by default or available as an option on managed services (cloud KMS). On kubeadm you configure it yourself.
      How it works
      An EncryptionConfiguration (provider kms v2 preferably, or aescbc) passed with --encryption-provider-config; then rewrite the existing Secrets.
      Limits and pitfalls
      Secrets created before you enabled it stay in plain text until they are rewritten (kubectl get secrets -A -o json | kubectl replace -f -).
      Exam tip
      A CKS topic.
      Supply chain securityControls on images: provenance, signature (cosign), vulnerability scanning, allowed registries, digests.
      Why it exists
      Only run images that your CI built and checked.
      In real companies
      Pipeline: build → scan (Trivy) → sign with cosign → deploy by digest; Kyverno verifyImages rejects unsigned images. This is exactly what the GitHub and GitLab courses of this series build.
      How it works
      image: registry/app@sha256:...; an admission policy that verifies signatures; imagePullSecrets for private registries.
      Limits and pitfalls
      A tag (even 1.0.0) can be overwritten; only the digest is immutable.
      Exam tip
      The Supply Chain Security domain of the CKS (20%).
      API auditingThe log of every request made to the API server: who, what, when, and the answer.
      Why it exists
      Investigate after an incident, prove compliance, detect abuse of permissions.
      In real companies
      Audit logs shipped to the SIEM; on clouds, enabled in the managed cluster options.
      How it works
      An audit policy (levels None, Metadata, Request, RequestResponse) passed with --audit-policy-file on kubeadm.
      Limits and pitfalls
      RequestResponse on everything produces huge volumes and can contain secrets.
      Where the images come from

      Admission policies can refuse unsigned images, but someone must sign them first. The two other courses of this series build exactly that supply chain, with scanning, SBOMs and cosign signatures: GitHub Actions DevSecOps and GitLab CI/CD DevSecOps.

      CustomResourceDefinition (CRD)The way to add new object types to the Kubernetes API (Certificate, HTTPRoute, ExternalSecret, Application...).
      Why it exists
      Extend Kubernetes with your own concepts, managed with the same tools (kubectl, RBAC, GitOps).
      In real companies
      Every platform tool (cert-manager, Argo CD, Prometheus Operator, Gateway API) ships its CRDs.
      How it works
      kubectl get crd; kubectl explain <type> works when a schema is provided. CRDs are cluster-wide.
      Limits and pitfalls
      Deleting a CRD deletes every object of that type. Helm does not upgrade the CRDs in a chart's crds/ folder: manage them separately.
      Exam tip
      "Understand CRDs, and install and configure operators" is in the CKA curriculum.
      OperatorsA custom controller plus CRDs that automate running a piece of software: install, upgrade, backup, failover.
      Why it exists
      Encode an administrator's know-how (for a database, for Kafka...) in code that runs in a loop.
      In real companies
      CloudNativePG (PostgreSQL), Strimzi (Kafka), cert-manager, Prometheus Operator, External Secrets.
      How it works
      Usually installed with Helm; you then create objects of the type it provides (kind: Cluster for CloudNativePG).
      Limits and pitfalls
      An operator is critical software you must upgrade and monitor: if it stops, nothing is managed any more.
      OwnerReferences, finalizers, garbage collectionAn OwnerReference links a parent to a child (Deployment → ReplicaSet → Pod). A finalizer is a marker that delays deletion until some clean-up is done.
      Why it exists
      Delete in cascade cleanly, and let controllers clean up external resources (load balancer, disk).
      In real companies
      A namespace stuck in Terminating for hours: often a finalizer of a controller that was uninstalled.
      How it works
      metadata.ownerReferences, metadata.finalizers. kubectl delete --cascade=orphan keeps the children.
      Limits and pitfalls
      Removing a finalizer by hand skips the clean-up: an external resource may be left orphaned.

      Helm: why, and how it works

      1 hour 30, the package manager of Kubernetes
      By the end of this station you can

      Lab 1 needed eleven files for one small app, with the same names and labels repeated everywhere, nothing to tell you what is installed, and no clean way to roll the whole app back.       Helm chartA package for a Kubernetes application: YAML templates, default values and metadata, versioned together.
      Why it exists
      Install a complete application (Deployment, Service, RBAC, HPA...) with one command, configurable per environment.
      In real companies
      Almost all third-party software (Prometheus, cert-manager, Argo CD, databases) installs from a chart; teams also package their own apps as internal charts pushed to an OCI registry.
      How it works
      Layout: Chart.yaml (chart version, appVersion), values.yaml, values.schema.json, templates/ (with _helpers.tpl, NOTES.txt, tests/), charts/ (dependencies), crds/.
      Limits and pitfalls
      version (of the chart) and appVersion (of the app) are two different things: bump version on every chart change.
      Releases and revisionsA named installation of a chart in a namespace. Every install, upgrade or rollback creates a revision.
      Why it exists
      Know what is deployed, with which values, and go back.
      In real companies
      One release per app and environment (kubelab-staging, kubelab-prod), often driven by Argo CD or Flux rather than by hand.
      How it works
      helm list -A, helm status, helm history, helm get values|manifest|notes. State is stored in Secrets named sh.helm.release.v1.<name>.v<N> in the release namespace.
      Limits and pitfalls
      Deleting those Secrets makes Helm "forget" the release without deleting the objects. A release stuck in pending-upgrade blocks every new upgrade (helm rollback unblocks it).
      ValuesThe parameters of a chart: defaults (values.yaml) overridden by files (-f) or --set.
      Why it exists
      One chart, many environments.
      In real companies
      values.yaml (safe defaults) + values-staging.yaml + values-prod.yaml versioned in git; never secrets in them.
      How it works
      Priority: values.yaml < -f file1 < -f file2 < --set. helm get values <release> --all shows the result. values.schema.json validates types and required fields.
      Limits and pitfalls
      --set with lists or dots in keys is tricky (--set-string, --set-json). --reuse-values reuses old values and ignores new defaults: prefer complete files.
      Templates (Go templates + Sprig)The YAML files in templates/ contain {{ }} expressions evaluated with .Values, .Release, .Chart, .Capabilities.
      Why it exists
      Generate manifests that adapt to the values: conditions, loops, defaults.
      In real companies
      Always check the rendered output in CI (helm template | kubeconform) before installing.
      How it works
      {{ .Values.x }}, if/else, range, with, include, toYaml, nindent, default, required, quote, b64enc, sha256sum. A dash ({{-) trims whitespace. helm template and helm install --dry-run=server show the result.
      Limits and pitfalls
      YAML indentation is the first source of errors: nindent is your friend. A template that is too clever becomes unreadable: keep charts simple.
      _helpers.tpl and standard labelsA file of reusable functions (define/include): full name, labels, selector, ServiceAccount name, image.
      Why it exists
      Consistent names and labels across every resource of the chart.
      In real companies
      app.kubernetes.io/* labels everywhere; selectors limited to name + instance (both stable).
      How it works
      {{- define "kubelab.labels" -}} ... {{- end }}, then {{- include "kubelab.labels" . | nindent 4 }}.
      Limits and pitfalls
      Never put the version in the selector labels: a Deployment's selector is immutable, so the upgrade would fail.
      HooksResources (often Jobs) run at a precise moment of the lifecycle: pre-install, post-install, pre-upgrade, post-upgrade, pre-delete, pre-rollback, test.
      Why it exists
      Migrate a database before the new pods, prepare or clean up.
      In real companies
      The kubelab chart runs a migration Job as a pre-install/pre-upgrade hook: if the migration fails, the new pods are not rolled out.
      How it works
      Annotations helm.sh/hook, helm.sh/hook-weight (order), helm.sh/hook-delete-policy (before-hook-creation, hook-succeeded, hook-failed).
      Limits and pitfalls
      Hooks are not part of the release: helm uninstall does not delete them unless a delete policy does. Argo CD maps them to its own hooks (check the behaviour).
      helm testPods annotated helm.sh/hook: test, run on demand to check that a release works.
      Why it exists
      A standard smoke test right after installing.
      In real companies
      In CI after helm upgrade --wait: helm test --logs; a failure raises an alert or triggers a rollback.
      How it works
      templates/tests/*.yaml; helm test <release> -n <ns> --logs.
      Limits and pitfalls
      It is not a functional test suite: keep the test short and reliable. Keep the test pod (no hook-succeeded delete policy) if you want --logs to find it.
      Dependencies (subcharts)Charts included in another one through the dependencies section of Chart.yaml.
      Why it exists
      Ship an app with its components (a cache, a dev database) or build an "umbrella" chart.
      In real companies
      An umbrella chart that assembles a platform's services; condition: redis.enabled to switch one on.
      How it works
      dependencies: name, version, repository (https:// or oci://), condition. helm dependency update downloads them into charts/ and writes Chart.lock. A subchart's values live under its key (redis.auth...).
      Limits and pitfalls
      A production database should not be a subchart of the app (its lifecycle is different).
      Chart repositories and OCI registriesWhere charts come from: classic HTTP repositories (index.yaml) or OCI registries (the same ones as for images).
      Why it exists
      Distribute and version charts like images.
      In real companies
      OCI is now the standard: internal charts pushed to Harbor, GitLab, GHCR, ECR, ACR, Artifact Registry, with the same permissions and scanning as images.
      How it works
      helm package chart/ → helm push kubelab-0.1.0.tgz oci://registry/charts → helm install x oci://registry/charts/kubelab --version 0.1.0. HTTP repos: helm repo add, helm repo update, helm search repo.
      Limits and pitfalls
      Always pin --version: without it Helm takes the latest published version.
      helm upgrade, --install, --wait, rollbackupgrade applies a new chart version or new values; rollback goes back to a revision.
      Why it exists
      Deploy repeatably and go back with one command.
      In real companies
      In CI/CD: helm upgrade --install x chart -f values-prod.yaml --wait --timeout 5m --rollback-on-failure (Helm 3's old --atomic); helm diff upgrade earlier, in the pull request.
      How it works
      --wait waits for resources to be ready (Helm 4 relies on kstatus). helm rollback x 3. helm history to choose the revision.
      Limits and pitfalls
      Without --wait, Helm reports success as soon as the API accepted the objects, even if the pods crash a minute later.
      The helm-diff pluginA plugin that shows the difference between the installed release and what an upgrade would apply.
      Why it exists
      Review an infrastructure change like a code diff.
      In real companies
      A mandatory step of manual deployment pipelines; Helmfile and Argo CD offer the same view.
      How it works
      With Helm 4, plugins are verified by signature: install from the published archive (helm plugin install https://github.com/databus23/helm-diff/releases/latest/download/helm-diff-linux-amd64.tgz, maintainer key imported) or, in a lab only, from the git URL with --verify=false. Then helm diff upgrade x chart -f values-prod.yaml.
      Limits and pitfalls
      Hide Secrets in CI output (--suppress-secrets).
      Helmfile and GitOpsHelmfile describes a set of releases and their values in YAML; Argo CD and Flux deploy charts from git continuously.
      Why it exists
      Stop running helm by hand: the desired state of a whole cluster lives in git.
      In real companies
      Company platforms: an Argo CD Application (OCI chart + values) or a Flux HelmRelease; Helmfile for teams without GitOps.
      How it works
      Argo CD renders the chart (helm template), applies it and watches for drift; Flux uses the Helm SDK and keeps a real release.
      Limits and pitfalls
      With Argo CD, helm list does not show the release (no Helm Secret): Argo CD is the source of truth.
      Helm 4The major version released in November 2025, succeeding Helm 3 (which gets security fixes until February 2027).
      Why it exists
      Modernize Helm: Server-Side Apply by default for new installs, readiness waiting through kstatus, a new plugin system (WASM), content-based chart cache.
      In real companies

      How it works

      kubeadmThe official tool to install and evolve a cluster: init, join, upgrade, certs, reset.
      Why it exists
      Build a conformant cluster on your own machines (on premises, VMs).
      In real companies
      On-premises clusters and labs; managed services (EKS, AKS, GKE) do this work for you. kind uses kubeadm inside its nodes.
      How it works
      kubeadm init --pod-network-cidr=... → install the CNI → kubeadm join on the workers (token + CA hash). The control plane runs as static pods (/etc/kubernetes/manifests).
      Limits and pitfalls
      The join token expires after 24 h (kubeadm token create --print-join-command). HA needs a stable control-plane endpoint (load balancer) from the very first init.
      Exam tip
      Installing and upgrading with kubeadm is the core of the Cluster Architecture domain (25%).
      cordon, drain, uncordoncordon: no new pod on the node. drain: cordon + evict the pods (respecting PDBs). uncordon: back in service.
      Why it exists
      Node maintenance: OS patching, kubelet upgrade, machine replacement.
      In real companies
      The standard procedure before touching a node; automated by managed node-pool upgrades.
      How it works
      kubectl drain n1 --ignore-daemonsets --delete-emptydir-data; kubectl uncordon n1.
      Limits and pitfalls
      A PDB that is too strict blocks the drain (it retries forever). Pods without a controller are lost (--force).
      Exam tip
      Upgrading a node: upgrade the kubeadm package → kubeadm upgrade node → drain → upgrade kubelet and kubectl → systemctl daemon-reload && systemctl restart kubelet → uncordon.
      Upgrading the clusterMoving to the next minor version of Kubernetes: control plane first, then the nodes, one minor version at a time.
      Why it exists
      Stay supported: each minor version is only maintained for about 14 months.
      In real companies
      One to three upgrades a year; test in staging first, check deprecated APIs (kubent, pluto) and add-on compatibility.
      How it works
      kubeadm upgrade plan → kubeadm upgrade apply v1.x.y (first control plane) → kubeadm upgrade node on every other node (secondary control planes and workers) → kubelet/kubectl on each node after a drain. On clouds: a button or Terraform, then the node pools.
      Limits and pitfalls
      You never skip a minor version. The kubelet must not be newer than the API server.
      Exam tip
      Likely in the exam.

      Limits and pitfalls
      Do not mix GitOps with manual kubectl apply: the agent overwrites manual changes (that is the point).
      Multi-tenancy and platformsSharing clusters safely between teams: namespaces, RBAC, quotas, NetworkPolicies, Pod Security, admission policies.
      Why it exists
      Offer teams guarded self-service instead of one cluster per team.
      In real companies
      A platform team that hands out ready-to-use namespaces through GitOps or a portal (Backstage), with automatic guardrails.
      How it works
      Pattern: one namespace per team/app/environment + a group RoleBinding + quota + LimitRange + default-deny + PSA restricted.

      A namespace does not isolate the kernel: for untrusted tenants, use separate clusters or vClusters.

      Focus on applications instead of PKI, etcd and control-plane availability.
      In real companies
      The vast majority of company clusters. kubeadm skills stay useful to understand what happens and for on premises.
      How it works
      Created with Terraform/OpenTofu; pod identity through the cloud's federation; load balancers, storage and DNS integrated.
      Limits and pitfalls

      Enterprise best practices

      45 minutes, the checklist a senior reviewer applies
      By the end of this station you can
      • review any application against the checklist companies use before production;
      • spot the seven most common anti-patterns and say what to do instead.

      This is the list a senior reviewer runs through before an application goes to production. The lab's manifests and chart follow it; tick it off against your own projects.

      • Images. Minimal (distroless), non-root, immutable tag or digest, scanned and signed in CI, private registry, imagePullPolicy: IfNotPresent.
      • Pods. Three suitable probes, requests on everything, a memory limit, a clean stop on SIGTERM, a restricted securityContext, a dedicated ServiceAccount without unnecessary token.
      • Availability. At least 2 replicas, topology spread across nodes and zones, a PDB, rolling updates that never lose capacity, an HPA on a meaningful metric.
      • Configuration. Nothing environment-specific in the image; secrets in a vault through External Secrets; a config checksum to roll pods.
      • Namespaces. One per app and environment, with group RBAC, ResourceQuota, LimitRange, Pod Security restricted and a default-deny NetworkPolicy.
      • Deployment. Everything in git; charts versioned in an OCI registry; Argo CD or Flux; no kubectl edit in production; changes reviewed in pull requests.
      • Observability. JSON logs on stdout, a /metrics endpoint, OpenTelemetry traces, app.kubernetes.io/* labels to tie metrics, logs and costs together.
      • Operations. Planned cluster upgrades, etcd and volumes backed up and restored in tests, certificates monitored, a runbook for every alert.
      • Policies. Kyverno or Gatekeeper: allowed registries, mandatory labels and limits, signed images, no latest, no privileged pods.

      Exam strategy

      Start with short, high-value tasks and never stay stuck more than 6 or 7 minutes. Begin every task with the ssh it names, and come back to the base machine when you are done. Generate YAML with --dry-run=client -o yaml. Verify every task (get, describe, auth can-i, a curl from a pod). Practise on the killer.sh simulator, and replay this lab's failure scenarios until each takes you less than three minutes.
